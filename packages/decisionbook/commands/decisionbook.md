# /decisionbook

Prepare this task with DecisionBook before you edit a protected file: $ARGUMENTS

Run each command below exactly as written, one per shell call: no `;`, `&&`, pipes or variables. Setup allowed `atlasbound decisionbook …` without a prompt (no git command: the host asks the person for those). What you record is read later by people and other AIs: plain words, no secrets. `new` and `add` take their JSON on standard input as a quoted heredoc, the form every fill-in is printed in (the call, `<<'JSON'`, the JSON on the next line, then `JSON` alone on the last): nothing inside a value needs shell quoting.

**The exact shape is handed to you.** The plan pack the task prompt gave ends with the fill-in JSON for this task's level and files (`atlasbound decisionbook plan <path|words>` prints the same). One `atlasbound decisionbook new` carries the plan; the person's answers are recorded by the product from their message. Every write prints its progress (rows met of rows asked) and only what it changed; `atlasbound decisionbook ready <id>` prints every missing row and the one add that fills them.

1. **Level.** `kind` is bug, feature, chore or refactor. Propose the level: `micro` is a small fix (one or two files, no risky path; or only tests, fixtures or docs): it needs its files and the person's yes, nothing else. `normal` is normal work: how success is seen, the files, a check with its command, the questions. `critical` is critical work (auth, money, data, schema or migration, infrastructure, many consumers): the whole form: 5 research records, the feature, actor, 3 edge cases, impact, tasks, risk, rollback, and at least 5 questions in fine detail. Code decides the level and says why; a database or danger-zone path is always critical. A level raised only by a soft signal drops back only when the person says so: `{"t":"waiver","reason":"<why it is not that risky>","by":"<their name>"}`.
2. **Research first, zero questions.** In this order:
   - the issue or task thread, read whole: every comment, what was decided there and by whom;
   - past plans of the area: the plan pack, then a node it names (`atlasbound decisionbook show file:<path>`); a past plan you use is named in the record that uses it (its id, or `decision:<key>`), and DecisionBook links the two;
   - a sideways search: `git log` of the files you will touch, and a search of the issues for the same words;
   - the code, read yourself: open each file you will change and the lines you need (Read, or `cat`, `sed`, `grep` on the file); a tool (any MCP server, a web or documentation tool) only points you at a file to open;
   - where it can run without editing a protected file, try the risky part (a console one-liner, the existing tests' baseline, a value at its limit and one either side): `{"t":"research","tool":"run","command":"<what you ran>","observed":"<what it printed or proved, cut>"}`.
   Record what you found: `{"t":"research","tool":"grep","asked":"<what you looked for>","answer":"<what it said>","source":"<file:line>"}`; a read that settles a fork adds `"settles":"<area.topic>"` and cites the line. Research counts only where its `source` names a file you read in this plan's sessions; a tool's answer is kept as a pointer, never research. Critical work needs five such records, no ceiling, and READY names the planned files you have not read yet. A question before any research is refused. What you found is carried to the next session, so write the answer, not the search.
3. **What to ask about** (a guide for your research and your questions, never records to fill): data that already exists under the old behaviour; unset, empty, malformed or hostile input; where each new setting is defined, defaulted and documented; other consumers and the upgrade path; what the user and the operator see when it fails; every entry point and the shape the person asked for in their own words; which tests prove each decision. Simulate the change along its files and note every edge and breakage: each one the code cannot settle is a question.
4. **Questions: only what the code cannot answer.** One per open behaviour: what a user sees or reads, a default, a limit, an edge, a preference, a trade-off, a product rule. Each names the decision it unlocks, why the code cannot answer it, and the answer you propose: `{"t":"question","q":"Q1","text":"<what research found; the options and what each changes>","decides":"<area.topic>","whyNotCode":"<why>","proposal":"<the answer you propose>","blocking":true}`. Normal work settles at least 3 forks, critical work at least 5 (a floor, never a ceiling). A task with fewer says so after the asking: `{"t":"item","kind":"no-fork","file":"<planned file>","text":"<what you read there and why nothing in it is the person's to choose>"}` per planned file. Never ask for a fact the repository holds, for what the task already says, or leave to edit a planned file. What you take as given to go on is an assumption, never an answer: `{"t":"assumption","text":"<what you assume>","why":"<why it seems safe>","q":"Q2"}`.
   **Ask a colleague.** When the person says someone else must answer ("go ask …"), write that question with `"to":"<who>"` and `"source":"<where it comes from>"`: it is parked, blocks nothing, and every session start names it until it is answered. Its answer is a decision with `"answers"`, `"said"` (their words, quoted) and `"source"` (where the quote is).
5. **Ask every open question in one message.** The plan in short, then every question still open, numbered, each in full: what the evidence showed, the options and what each changes, and the answer you propose in the question's own words. With many, group them under short headings; never split them over messages and never hold one back. Ask each as a question the person answers: do not offer to take your proposals as a whole (no "accept all", no one yes over several questions): a proposal is your guess until they answer it. Then stop and wait; a second round asks only what their answers opened. The product records their answers itself from their message, where the message ties an answer to its question (a list item that quotes the question; a reply that on their own takes your proposals whole is recorded too, each marked as taken whole), and tells you which it recorded: check them against what you read, do not send them again. Only an answer it could not place goes in an `atlasbound decisionbook add <id>` as a decision: `"answers"` its q, `"said"` their own whole sentence, `"value"` in their words, `"effect"` what it changed in the plan. Their answers to every blocking question are their yes; you never ask them to type a command, and you never write a yes they did not give.
6. **READY is the freeze.** The plan is now the settled intake: build from it. Edits inside it pass in silence. A file you did not plan joins the plan by itself (one line tells you). Only a danger path outside the plan (a danger zone, a database schema or migration) asks the person once. If the research filled the context, tell the person to `/clear`: the next session starts from the frozen plan (its decisions with their sentences, its files, what the research found) and builds, with no new plan and no new yes.
7. **Other work on the same branch.** The branch's open plan is the work in progress whatever the first message says. Only if the person's message plainly names other work: ask them in plain words whether that plan is set aside, record their answer on it (`{"t":"aside","by":"<their name>","said":"<their whole sentence>"}`), then plan the other work with one `atlasbound decisionbook new`.
8. **Read once, then walk.** `atlasbound decisionbook show <id>` gives the whole plan once per session and its node map; after that fetch one node: `atlasbound decisionbook show <id> decisions`, `atlasbound decisionbook show <id> research`.
9. When the work is done and its commits exist, on its branch as it is then, before it is merged or copied: `atlasbound decisionbook close <id>` records its own commits, files and tests.
