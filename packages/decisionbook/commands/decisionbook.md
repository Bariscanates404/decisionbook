# /decisionbook

Prepare this task with DecisionBook before you edit a protected file: $ARGUMENTS

Run each command below exactly as written, one per shell call: no `;`, `&&`, pipes or variables. Setup allowed `atlasbound decisionbook …` and your Write tool in `.atlasbound/drafts/` without a prompt (no git command: the host asks the person for those). What you record is read later by people and other AIs: plain words, no secrets. `new` and `add` take their JSON from a draft file, the form every fill-in is printed in: write the JSON with your Write tool to `<id>.json` (`new.json` for a new plan) in your session's own folder under `.atlasbound/drafts/` (every DecisionBook reply and refusal names it: `<drafts>`), then run `atlasbound decisionbook add <id> --file <drafts><id>.json` (or `new --file <drafts>new.json`): another session's draft is never read. Never put the JSON on the command line. The product removes the draft once it is written; a refused one stays: fix it with your Edit tool (never `sed` or a script: the host asks the person for those) and run the call again.

**The exact shape is handed to you.** The plan pack the task prompt gave ends with the fill-in JSON for this task's level and files (`atlasbound decisionbook plan <path|words>` prints the same). One `atlasbound decisionbook new` carries the plan; you record the person's answers, each with their own words. Every write prints its progress (rows met of rows asked) and only what it changed; `atlasbound decisionbook ready <id>` prints every missing row and the one add that fills them.

1. **Level.** `kind` is bug, feature, chore or refactor. Propose the level: `micro` is a small fix (one or two files, no risky path; or only tests, fixtures or docs): it needs its files and the person's yes; a value their message sets is still recorded as their decision (step 5). `normal` is normal work: how success is seen, the files, a check with its command, the questions. `critical` is critical work (auth, money, data, schema or migration, infrastructure, many consumers): the whole form: 5 research records, the feature, actor, 3 edge cases, impact, tasks, risk, rollback, and at least 5 questions in fine detail. Code decides the level from the paths you plan, never from the plan's words, and says why: a database or danger-zone path is always critical, and a path in a risk area (a folder or file named auth, login, billing, payment, checkout and the like, or one the repository's own `risk` list names) is critical unless the person waives it. A level raised only by a soft signal drops back only when the person says so: `{"t":"waiver","reason":"<why it is not that risky>","by":"","said":"<their own words, copied from their message>"}`; leave `"by"` empty: the product writes who waived, and only their own words waive.
2. **Research first, zero questions.** In this order:
   - the issue or task thread, read whole: every comment, what was decided there and by whom. A rule its owner already answered there is not asked again: record it as theirs, with the comment's address as its `"source"`, by the rule of whose words a decision holds (step 4). The plan is linked to the issue the person's message or the branch names (`for issue:#N`, written by DecisionBook); for another issue add `{"t":"link","rel":"for","to":"issue:#N","why":""}`;
   - past plans of the area: the plan pack, then a node it names (`atlasbound decisionbook show file:<path>`); a past plan you use is named in the record that uses it (its id, or `decision:<key>`), and DecisionBook links the two;
   - a sideways search: `git log` of the files you will touch, and a search of the issues for the same words;
   - the code, read yourself: open each file you will change and the lines you need (Read, or `cat`, `sed`, `grep` on the file); a tool (any MCP server, a web or documentation tool) only points you at a file to open;
   - where it can run without editing a protected file, try the risky part (a console one-liner, the existing tests' baseline, a value at its limit and one either side): `{"t":"research","tool":"run","command":"<what you ran>","observed":"<what it printed or proved, cut>"}`.
   Record what you found: `{"t":"research","tool":"grep","asked":"<what you looked for>","answer":"<what it said>","source":"<file:line>"}`; a read that settles a fork adds `"settles":"<area.topic>"` and cites the line. Research counts only where its `source` names a file you read in this plan's sessions; a tool's answer is kept as a pointer, never research. Critical work needs five such records, no ceiling, and READY names the planned files you have not read yet. A question before any research is refused. What you found is carried to the next session, so write the answer, not the search.
3. **What to look for** (a guide for your research, and for a question only where a human must decide; never records to fill): data that already exists under the old behaviour; unset, empty, malformed or hostile input; where each new setting is defined, defaulted and documented; other consumers and the upgrade path; what the user and the operator see when it fails; every entry point and the shape the person asked for in their own words; which tests prove each decision. Simulate the change along its files and note every edge and breakage: each one the code cannot settle is a question.
4. **Questions: only what the code cannot answer and a human must decide.** A business or product rule; what a user, a customer or an operator will see, pay or lose; a trade-off of scope, cost or risk; a preference only they hold. Never invent such a rule, and never guess it: it is a question. Each names the decision it unlocks, why the code cannot answer it, and the answer you propose: `{"t":"question","q":"Q1","text":"<what research found; the options and what each changes>","decides":"<area.topic>","whyNotCode":"<why>","proposal":"<the answer you propose>","blocking":true}`.
   **An implementation choice is yours, never a question**: a signature, where a type or a file lives, a name, the shape of an internal value, how an error is raised, a convention the repository already shows. State each as what you will do: `{"t":"assumption","text":"<what you will do>","why":"<the precedent or the reason>"}`, and show them to the person with the plan as a short list they can object to; where they object, their words are their decision.
   Normal work settles at least 3 forks, critical work at least 5, by research that cites the line or by a person's answer. Never ask to reach the number: a task with fewer decisions of a human's says so, `{"t":"item","kind":"no-fork","file":"<planned file>","text":"<what you read there and why nothing in it is the person's to choose>"}` per planned file. Never ask for a fact the repository holds, for what the task already says, or leave to edit a planned file.
   **Replacing a standing decision.** A decision the plan pack lists as a person's is changed by the person only. Where your change leaves one as it is, say so in a non-goal item (`{"t":"item","kind":"non-goal","text":"<why>","covers":["<its plan id>/<key>"]}`) and do not ask whether it stays. When the task goes against one, ask them in a question that names it (`"supersedes":["<its plan id>/<key>"]`; the plan id: `atlasbound decisionbook show decision:<key>`): its text says the old decision whole, its `"proposal"` is the whole decision as it would hold after (every part that stays, and what changes). You read their answer and say which it is, on the decision that records it: `"supersedes":["<ref>"]` where their answer replaces the old one (`"value"`: the whole decision as it holds now); `"keeps":["<ref>"]` where they keep it (`"value"`: the old decision; nothing is replaced, and you then tell them what the plan does instead and ask whether to go ahead). One of the two is needed. A decision of theirs may name what it replaces without such a question, when their own words say so. A decision of yours never replaces a person's: it is refused.
   **Who answers.** The person, unless a source names someone else as the one who owns the answer: the issue or a comment on it ("Emma (BA) will confirm the rounding"), a document, or the person's own sentence ("go ask …"). Then the question carries `"to":"<who>"` and `"source":"<where they are named>"`: it is parked, blocks nothing, and every session start names it until it is answered (by that one's words, or by the person's own answer). With no such source it is the person's question, whoever you think owns the rule: they answer it, or say who does.
   **Whose words a decision holds.** With the person's task message, and again when they answer, DecisionBook hands you the one rule of whose words a decision holds, with its examples: follow that text, it is the only place the rule is written. Each decision is one record with `"whose"` and `"said"`, in an answer and in a value a message states alike; the product writes who recorded it and where it was said.
5. **Ask every open question in one message.** The plan in short, then every question still open, numbered, each in full: what the evidence showed, the options and what each changes, and the answer you propose in the question's own words; after them, your assumptions as a short list (what you will do unless they say otherwise). With many, group them under short headings; never split them over messages and never hold one back. Ask each as a question the person answers: do not offer to take your proposals as a whole (no "accept all", no one yes over several questions): a proposal is your guess until they answer it. Then stop and wait; a second round asks only what their answers opened. **Record what they answered in the turn you read it**: one `atlasbound decisionbook add <id>` with one decision per question their message answers: `"answers"` its q, `"key"` that question's `decides` (to change one, write its key again naming it: `"supersedes":["<id>/<key>"]`, never a new key), `"value"` what you understood was decided (left out where they took your proposal as it is: the product writes the proposal; where one reply answers several questions, one decision each), `"whose"` and `"said"` by that rule, `"effect"` what it changed in the plan. You decide what they meant. Words found neither in a message they typed nor at the source are refused, and the refusal says which words were not found where; the reply shows each decision with whose it is and its words. Ask in plain words they answer by typing: an answer picked in a question dialog is not a typed message. A question their message leaves open gets no decision: ask it again. Their answers to every blocking question are their yes; you never ask them to type a command, and you never write a yes they did not give.
   **A value the person states.** When their message itself sets a value ("the fee is 100", "make it 200") or says one stays ("keep it at 100"), that is a decision at every level, with no question: `"whose":"person"` and `"said"` their own words, or `"whose"` the teammate's name where the message gives that one's words ("Emma wants it capped at 500"). A value you proposed or asked about in chat that they settle with a word ("ok", "keep it") is their decision too: record it, `"said"` that word. Where they put a question off ("as a todo", "not sure yet") nothing is settled: record `{"t":"later","answers":"<its q>","said":"<their words>"}`, never a decision, and the question stays open. Where the plan pack lists a decision of the same thing, write it under that key and name it: `"supersedes"` where their words change it, `"keeps"` where they keep it. A keep is recorded also when no code changes; in the plan that holds the decision it keeps, it takes a key of its own (`<key>.kept`).
6. **READY is the freeze.** The plan is now the settled intake: build from it. Edits inside it pass in silence. A protected file the plan does not name is asked: the person's yes to that edit adds the file to the plan, or you open a new plan for it with one `atlasbound decisionbook new`. If a file added that way raises the plan's level, the plan covers no edit until it holds that level's rows (`atlasbound decisionbook ready <id>` prints them). A danger path outside the plan (a danger zone, a database schema or migration) asks the person once. If the research filled the context, tell the person to `/clear`: the next session starts from the frozen plan (its decisions with their sentences, its files, what the research found) and builds, with no new plan and no new yes.
7. **Other work on the same branch.** A draft another session or a teammate left open is named in one line; when the person's task is on none of its files, plan it beside that draft with one `atlasbound decisionbook new` naming its files, and ask them nothing about the draft first. A READY plan is the work in progress. A plan that came with a teammate's commit is theirs: plan the person's task beside it with its own `atlasbound decisionbook new`, never close it, and never write the person's decision over a line the teammate wrote (name that line from your plan instead). Only when the person says to set a plan aside: record it on that plan with their own words (`{"t":"aside","by":"","said":"<their own words>"}`); if they have not said so, ask them.
8. **Read once, then walk.** `atlasbound decisionbook show <id>` gives the whole plan once per session and its node map; after that fetch one node: `atlasbound decisionbook show <id> decisions`, `atlasbound decisionbook show <id> research`.
9. When the work is done, before its commit, on its branch as it is then (before it is merged or copied): `atlasbound decisionbook close <id>` records what shipped, the plan's own commits and the changed files not committed yet with their tests, and prints one `git add …`, `git commit …` command; give the person that command as printed, so one commit carries the code and the plan. The product never commits. A turn that ends on finished work with no close is held once and told this; a later message of the person is told the commit that waits. Until that commit is made the plan stays open: after a further edit, close again and the new record takes the old one's place. Work committed before the close goes the same way: where no other branch, remote or tag holds its last commit the printed command amends the record into it, else the record is one more commit, said as such.
